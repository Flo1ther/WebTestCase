# Як повністю працює помічник ШІ у WebTestCase

> Актуальний опис **AI QA Copilot** — контекстний review, керовані виправлення, coverage, API-підказки та benchmark — наведено в [AI_COPILOT_UK.md](AI_COPILOT_UK.md). Цей документ зберігає базове пояснення режимів.

Актуальний стан залежить від `.env`. У поточному локальному середовищі доступна Ollama з `qwen2.5:1.5b`; водночас детерміновані правила завжди дають перевірюваний базовий результат. Режим і модель прямо показані на сторінці «Помічник ШІ».

## Чому раніше навіть повний тесткейс отримував поради

Це була властивість реалізації, а не доказ недоліків вашого тесткейсу:

1. `_local_analysis` шукав англійське слово `error` лише в описі та підсумковому результаті. Якщо його не було, завжди рекомендував негативний сценарій. Український опис помилки або позитивний сценарій без жодної помилки також потрапляли під це правило.
2. Менше двох кроків автоматично трактувалося як недолік. Насправді одного конкретного кроку з перевірним результатом може вистачати.
3. Навіть коли список зауважень був порожнім, код заповнював його загальною фразою про конкретизацію результатів. Порожнього списку порад фактично не існувало.
4. Генератор локального режиму не розбирав повний введений сценарій. Він повертав загальні шаблони «Happy path / Validation / Boundary», вставляючи опис у назву, та мав дію на кшталт «Perform the relevant user action».
5. Генерація зберігала запис пропозиції, але не створювала реального TestCase. Кнопка аналізу в картці перевіряла збережений TestCase, а не довільний текст із генератора. Це два різні джерела даних.

Усі ці причини виправлено. Повний сценарій може отримати **«За перевіреними правилами структурних недоліків не виявлено»**, порожні `findings`, `risks`, `improvements` та `optional_suggestions`. Негативний сценарій не є обов’язковою частиною позитивного тесткейсу.

## Два різні режими

| Властивість | Локальні правила | Зовнішня модель |
|---|---|---|
| Налаштування | `AI_PROVIDER=local` | Інше значення AI_PROVIDER та API-ключ |
| Мовна модель | Немає | Вказана в AI_MODEL |
| Мережевий запит | Немає | HTTPS до AI_API_BASE_URL |
| Розуміння довільної вимоги | Не заявляється | Модель інтерпретує наданий текст, може помилятися |
| Перевірка тесткейсу | Чіткі структурні правила | Аналіз опису з конкретними полями та цитатами |
| Створення з готового тексту | Розбір явно названих секцій | Структурування природною мовою |
| Виконання тесту | Немає | Немає |
| Навчання на базі проєкту | Немає | Застосунок не навчає модель і не відправляє всю базу |

Якщо вибрана Ollama або зовнішня модель недоступна, review повертає позначений `deterministic_fallback`: формальні докази залишаються доступними, але семантичний висновок LLM не вигадується. Назва моделі у конфігурації — це налаштування, а не підтвердження того, що зовнішній запит уже виконувався.

## Аналіз із картки тесткейсу

1. Користувач натискає «Проаналізувати за допомогою ШІ».
2. Frontend відправляє `POST /api/ai/analyze-test-case/` із `test_case_id`.
3. Backend перевіряє сеанс, підтвердження email, роль та доступ до цього TestCase. TESTER може аналізувати лише призначені йому сценарії; ADMIN і MANAGER — доступні їм записи.
4. Сервер читає **назву, опис, передумови, підсумковий результат і всі збережені кроки з їхніми очікуваними результатами**, а також обмежений контекст проєкту: Requirements, схожі кейси, Suites, виконання та дефекти. Незбережені зміни у формі не входять в аналіз.
5. Схожі на секрети фрагменти `password: ...`, `пароль=...`, `token`, `secret`, `api_key` маскуються. Це обмежений захист, а не універсальний DLP: не вводьте справжні приватні дані в тестові описи.
6. Виконується локальна перевірка або зовнішній запит відповідно до конфігурації.
7. Запис AIAnalysis зберігає результат, провайдера, назву моделі, автора, час, хеш наданого опису та дату версії тесткейсу. Аудит записує тип дії й ID аналізу, а не API-ключ чи пароль.
8. Frontend показує режим, межі перевірки та конкретні зауваження. Якщо тесткейс змінено після аналізу, в картці позначається застарілий результат.

Локальні правила перевіряють порожні основні поля, відсутність кроків, відсутність дії/результату кроку та кілька відомих шаблонних дій. Вони **не визначають**, чи правильна бізнес-логіка, чи існує кнопка на сайті й чи повний набір тестів для продукту. «Немає структурних зауважень» означає тільки проходження цих правил.

## Що отримує зовнішня модель

До провайдера надходять інструкція аналізу українською та обмежений JSON вибраного тесткейсу з релевантним контекстом. Не передаються паролі входу, TOTP-секрети, cookies, журнали входу чи файли користувача. Застосунок не дає моделі інструментів для виконання коду або операцій із базою.

Модель має повернути JSON з `summary`, `findings`, `optional_suggestions`. Для кожного зауваження потрібні `field`, дослівний `evidence`, `reason`, `recommendation`. Сервер перевіряє типи, довжину, існування поля та наявність цитати в цьому полі. Порожня цитата допускається лише для порожнього поля. Невідповідна структура чи вигадана цитата дають помилку, а не демонстраційний запасний висновок.

Перевірка цитати не доводить істинність усіх міркувань моделі. Людина все одно оцінює рекомендацію. Модель може мати інший погляд на якість, але інструкція прямо дозволяє нуль зауважень і забороняє вигадувати поради заради відповіді. Необов’язкове розширення покриття відображається окремо від підтвердженого недоліку.

## Підготовка нового тесткейсу

На сторінці «Помічник ШІ» генератор отримує **тільки введений опис**, а не автоматичний контекст усіх проєктів. Число пропозицій — верхня межа, а не вимога вигадати стільки різних сценаріїв.

У локальному режимі використовуйте явний формат:

```text
Назва: Збереження імені профілю
Опис: Перевірити збереження нового імені після оновлення сторінки.
Передумови: Користувач увійшов, email підтверджено, профіль відкрито.
Кроки:
1. Увести ім’я Олена та натиснути Зберегти => Показано повідомлення про збереження.
2. Оновити сторінку => У полі імені відображається Олена.
Очікуваний результат: Нове ім’я збережено та відображається після оновлення.
```

Роздільником дії та результату кроку може бути `=>` або `→`. Підтримуються також англійські назви секцій. Секція «Опис» може бути відсутня — тоді її зміст береться з назви; відсутні критичні секції та результати кроків запитуються як уточнення. Без достатніх даних локальний конструктор **не** підставляє вигаданих шаблонів. Якщо повністю описано один сценарій, повертається один, навіть коли максимум пропозицій дорівнює трьом.

Після підготовки ви бачите всі поля й кроки. Щоб створити запис у базі, оберіть проєкт і натисніть **«Створити тесткейс у проєкті»**. Сервер повторно перевіряє права й валідує пропозицію звичайним TestCaseSerializer. Створюється реальний тесткейс зі станом `NOT_RUN`; повторне натискання на ту саму пропозицію повертає вже створений ID замість дублювання. Чужу пропозицію може прийняти її автор-менеджер або ADMIN; TESTER не створює записи цим шляхом.

Потім відкрийте новий тесткейс і запустіть аналіз. Тепер це точно той сценарій, який ви підготували й зберегли, а не інший запис із бази. На повному прикладі вище регресійний тест і реальна HTTP-перевірка підтвердили порожній список зауважень.

## Аналітика — окремий механізм

Графіки виконань, покриття, дефектів і користувачів рахуються Django ORM із PostgreSQL. Це не відповідь ШІ. Позначка стабільності також визначається правилами: останні шість виконань, частка невдач, перехід PASSED→FAILED, повторні блокування та відсутність свіжого виконання протягом 30 днів. Тому аналітичний статус «Потребує уваги» може існувати навіть у структурно повного тесткейсу. Він стосується історії запусків, а не якості його опису.

Стан виконання змінюється тільки через передбачені операції системи, наприклад збереження фактичного результату тестувальником. Кнопка ШІ не встановлює PASSED, не створює дефект і не запускає браузерні тести.

## Налаштування й перевірка

### Реальна локальна модель через Ollama

Ollama дозволяє запускати мовну модель на власному комп'ютері. Дані тесткейсу залишаються на `127.0.0.1` і не передаються у зовнішній API. Після встановлення Ollama та завантаження моделі потрібно встановити в `.env`:

```dotenv
AI_PROVIDER=ollama
AI_MODEL=qwen2.5:3b
OLLAMA_API_URL=http://127.0.0.1:11434/api/chat
AI_TIMEOUT=90
```

Потім перезапустіть backend. У сторінці «Помічник ШІ» буде показано «Локальна мовна модель Ollama», а в історії аналізів `provider` матиме значення `ollama`. Якщо сервер або модель недоступні, API поверне контрольовану помилку; локальні правила автоматично не підставляються.

Для зовнішньої моделі задайте `AI_PROVIDER=external`, `AI_API_KEY`, `AI_MODEL` і HTTPS `AI_API_BASE_URL` сумісного Chat Completions API з JSON object response. Вкажіть реальний ID моделі вашого провайдера, а не `testflow-local-demo`, і перезапустіть backend. Увесь цей режим потребує ключів; справжній зовнішній запит у цьому середовищі **не перевірявся**. Помилки мережі, таймаути, неправильна схема та недійсні цитати обробляються як недоступність провайдера.

Для запитів діють рольові обмеження, CSRF, ліміт 20 операцій за годину, постійний лічильник акаунт+IP у PostgreSQL і аудит. Тривалий мережевий запит виконується до транзакції збереження результату, щоб не тримати відкриту транзакцію БД під час очікування провайдера.

Ключові файли: `apps/ai_assistant/services.py`, `views.py`, `serializers.py`, `models.py`; UI — `frontend/src/pages/AIAssistant.tsx`, `TestCaseDetail.tsx`, `components/AIResult.tsx`. Регресії — `tests/test_ai_quality.py`, живий сценарій — `scripts/live_check.py`.
