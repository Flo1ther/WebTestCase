# Лабораторна робота 8–10 — реалізація backend програмного продукту

## Тема

Реалізація серверної частини платформи керування тестуванням TestFlow.

## Реалізований функціонал

TestFlow використовує багаторівневу архітектуру: React/Vite клієнт надсилає cookie+CSRF захищені запити до Django REST Framework; serializers виконують валідацію; views і сервісний шар реалізують бізнес-правила; Django ORM зберігає дані у PostgreSQL. Авторизація та рольові обмеження перевіряються на сервері.

Реалізовано проєкти, вимоги, Test Suites, тесткейси, тестові прогони, ручні виконання, дефекти, API-тести, аудит, звіти й аналітику. Requirement пов’язується з Test Case; Test Suite групує тесткейси одного проєкту; Test Run містить вибрані тесткейси; TestExecution зберігає незмінний історичний результат; Defect може бути пов’язаний із Test Case та Test Run.

## API Testing

Модуль API Testing зберігає HTTP method, URL, headers, JSON body, expected status та JSON assertions. Runner виконує реальний HTTP-запит, зберігає фактичний status, тривалість, обмежений preview відповіді та результати assertions. PASS/FAIL визначає алгоритм порівняння, а не LLM.

Для захисту від SSRF runner приймає лише `http://localhost` та `http://127.0.0.1`, має timeout 10 секунд, не передає Authorization і Cookie. Demo API `demo-store` містить задокументований дефект DEMO-API-01: checkout приймає невалідний payment token і помилково повертає HTTP 201. API-тест із очікуванням HTTP 400 отримує реальний FAIL.

## AI QA Copilot

AI-сервіс є окремим backend-шаром із конфігурованим провайдером, обмеженням розміру відповіді, перевіркою JSON-схеми, таймаутами та аудитом. Локальна Ollama не надсилає дані поза localhost. Зовнішній режим потребує API key у backend environment; ключ ніколи не передається frontend. Якщо LLM недоступна, review не зникає: запускається явно позначений deterministic fallback, який не видається за відповідь мовної моделі.

Copilot збирає обмежений контекст: тесткейс, проєкт, Requirements, схожі кейси, Suites, виконання та дефекти. Він повертає findings із категорією, критичністю, доказом, полем, обґрунтуванням, рекомендацією й, коли зміна однозначна, Before/After. Виправлення мають стан PROPOSED/APPLIED/REJECTED; користувач може відредагувати текст, прийняти або відхилити зміну. Optimistic locking за `updated_at` не дозволяє перезаписати тесткейс, який змінився після review.

Окремі вкладки AI QA Copilot підтримують генерацію чернеток за типом/пріоритетом/деталізацією/Suite/API endpoint; аналіз Requirement→Test Case coverage із позначенням лише потенційних прогалин; пояснення API runner failures і пропозиції assertions. AI не запускає endpoint та не визначає PASS/FAIL — це робить API runner. Відтворюваний benchmark із шести контрольних записів обчислює Precision/Recall/F1 для `qa-review-rules-v1`; ці метрики не є оцінкою LLM.

## Demonstration scenario

1. Запустити PostgreSQL, backend і frontend.
2. Виконати `python manage.py seed_quality_demo`.
3. У Requirements відкрити `REQ-CHECKOUT-01` та показати зв’язаний критичний Test Case.
4. У Test Runs показати `Demo Store release 1.0`.
5. У API Testing запустити `Checkout rejects invalid token`.
6. Показати фактичний HTTP 201 проти очікуваного 400 та FAIL assertion.
7. Створити Defect, заповнивши actual result, expected result, severity, version та environment.
8. Показати Dashboard: покриття вимог, прогрес, активні критичні дефекти та test runs.

## Перевірка

Перевірено Django system check, відсутність неприменених migrations, Vite production build, demo API tests, API runner tests і traceability tests. Контрольні тести перевіряють SSRF-відхилення, PASS assertion, контрольований API defect, ізоляцію проєктів Requirement/Test Case і Test Run/Test Case.

## Обмеження

Універсальний доступ до зовнішніх API навмисно не ввімкнено: runner обмежений локальними сервісами. Повноцінна якість генерації українських тестів потребує достатньо потужної локальної LLM або налаштованого зовнішнього провайдера. Локальна модель не використовується для визначення PASS/FAIL або вигадування доказів дефекту.
